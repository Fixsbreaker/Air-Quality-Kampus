# KBTU Air Quality Kampus

Сервис мониторинга и прогноза качества воздуха на кампусе КБТУ.

Алматы стабильно входит в число городов с самым грязным воздухом, но у университета
нет инструмента, который отвечал бы на два практических вопроса: **можно ли сегодня
проводить занятия спортом на улице** и **можно ли открывать окна в аудиториях**.
Проект собирает данные о концентрации PM2.5 и PM10 по точкам кампуса, считает индекс
AQI по методике US EPA, строит прогноз на 48 часов и превращает число в конкретное
действие.

Отличие от существующих ESG-проектов КБТУ: они считают то, что университет
*выбрасывает* (CO₂, отходы, энергия). Этот считает то, чем студенты *дышат*.

## Возможности

| Что | Как это выглядит |
|---|---|
| Текущее состояние воздуха | Крупная плашка AQI с цветом по шкале US EPA и текстовой рекомендацией |
| Ответ на практический вопрос | Флаги «спорт на улице», «открывать окна», «нужна маска» |
| История наблюдений | График AQI / PM2.5 / PM10 за сутки, трое суток, неделю, месяц |
| Прогноз на 48 часов | График прогноза и явное указание часа пикового загрязнения |
| Карта города | Учебный корпус и общежития, раскрашенные по текущему AQI |
| Telegram-бот | `/now`, `/forecast`, `/subscribe`, утренний дайджест 07:30, алерт при превышении порога |
| Выгрузка для администрации | CSV-отчёт за период по всем точкам |

## Архитектура

```
                    ┌──────────────────┐
                    │  Open-Meteo API  │  качество воздуха + погода
                    └────────┬─────────┘
                             │ httpx, раз в час (APScheduler)
                    ┌────────▼─────────┐
                    │  worker          │  сбор → очистка → расчёт AQI
                    │  (парсер + ML)   │  прогноз, ночное переобучение
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │   PostgreSQL     │  measurements, weather, forecasts,
                    │                  │  users, alerts, model_runs
                    └────────┬─────────┘
                             │            ┌─────────────┐
                             ├────────────│  Redis      │ кэш ответов
                             │            └─────────────┘
                             │ SQLAlchemy
                    ┌────────▼─────────┐
                    │   FastAPI        │  /api/current, /history, /forecast,
                    │   + Swagger      │  /subscribe, /admin/report
                    └───┬──────────┬───┘
                        │          │
             ┌──────────▼──┐   ┌───▼────────────┐
             │ React SPA   │   │ Telegram-бот   │
             │ Recharts    │   │ aiogram 3      │
             │ Leaflet     │   │                │
             └─────────────┘   └────────────────┘
```

Ключевое архитектурное решение: **вся доменная логика живёт в API**. Бот и дашборд —
тонкие слои представления. Расчёт AQI и правила рекомендаций существуют в одном месте,
поэтому в мессенджере и на сайте пользователь гарантированно видит одинаковый ответ.

Второе решение: **прогноз не считается на лету**. Фоновая задача раз в час пишет
результат модели в таблицу `forecasts`, а `/api/forecast` только читает её. Веб-процесс
остаётся быстрым, а тяжёлые вычисления не блокируют запросы.

## Быстрый старт

Нужен только Docker.

```bash
make init
```

```bash
make up
```

Через минуту доступны:

| Адрес | Что это |
|---|---|
| http://localhost:5173 | Дашборд |
| http://localhost:8000/docs | Swagger UI |
| http://localhost:8000/health | Проверка состояния сервиса |

Дальше нужно наполнить базу и обучить модель:

```bash
make backfill DAYS=730
```

```bash
make train
```

```bash
make forecast
```

Запуск бота (нужен `BOT_TOKEN` от [@BotFather](https://t.me/BotFather) в `.env`):

```bash
docker compose --profile bot up -d bot
```

Полный список команд — `make help`.

## Локальная разработка без Docker

```bash
cd backend && python3.11 -m venv .venv && source .venv/bin/activate && pip install -r requirements-dev.txt
```

Поднять только базу:

```bash
docker compose up -d db
```

Указать в `.env` хост базы `localhost` вместо `db`, накатить миграции и запустить API:

```bash
cd backend && alembic upgrade head && uvicorn app.main:app --reload
```

Фронтенд:

```bash
cd frontend && npm install && npm run dev
```

> **macOS:** LightGBM требует библиотеку OpenMP — `brew install libomp`. Если её нет,
> проект не падает: обучение автоматически переключается на
> `HistGradientBoostingRegressor` из scikit-learn (алгоритм по сути тот же).

### Логика рекомендаций

| AQI | Категория | Рекомендация |
|---|---|---|
| 0–50 | Хорошо | Занятия на улице без ограничений |
| 51–100 | Умеренно | Норма; чувствительным людям — сократить нагрузку |
| 101–150 | Вредно для чувствительных | Физкультуру перенести в зал; астматикам — маска |
| 151–200 | Вредно | Отменить занятия на улице, закрыть окна, включить рециркуляцию |
| 200+ | Очень вредно | Минимизировать выход на улицу |

## Модель прогноза

**Постановка.** Прямое многогоризонтное прогнозирование: вместо 48 отдельных моделей
обучается одна, а номер горизонта подаётся ей как признак.

**Признаки (40 штук):** лаги PM2.5 (1, 2, 3, 6, 12, 24, 48 ч), скользящие среднее,
стандартное отклонение и максимум по окнам 3/6/24 ч, разности, погода (температура,
скорость ветра, влажность, давление), направление ветра через синус и косинус,
календарь (час суток циклически, день недели, выходной, месяц), флаг отопительного
сезона и one-hot локации.

**Валидация.** Расширяющееся окно по времени с **зазором в 48 часов** между обучающей
и тестовой выборкой. Зазор обязателен: строка за момент `t` с горизонтом 48 имеет цель
в момент `t + 48`, и без зазора часть целей обучающих строк попала бы в тестовый
период — это утечка будущего.

**Результаты** (LightGBM, годовой архив, 417 246 строк, 4 фолда):

| Модель | MAE, мкг/м³ | RMSE, мкг/м³ | MAPE, % |
|---|---|---|---|
| Persistence («будет как сейчас») | 10.58 | 14.57 | 51.5 |
| Seasonal naive («как в тот же час вчера») | 8.46 | 11.60 | 42.3 |
| **LightGBM** | **7.77** | **11.13** | **34.3** |

Разбивка по горизонтам относительно persistence:

| Горизонт | MAE модели | MAE baseline | Выигрыш |
|---|---|---|---|
| 1 ч | 1.78 | 1.31 | −36 % |
| 3 ч | 2.78 | 3.08 | +9 % |
| 6 ч | 3.62 | 4.52 | +20 % |
| 12 ч | 3.97 | 5.30 | +25 % |
| 24 ч | 4.29 | 4.93 | +13 % |
| 36 ч | 4.21 | 6.12 | +31 % |
| 48 ч | 4.17 | 5.38 | +23 % |

Два честных наблюдения. Во-первых, **на горизонте 1 час наивный прогноз лучше модели**:
за час концентрация почти не меняется, и инерция побеждает. Модель начинает выигрывать
с трёх часов — то есть ровно там, где от прогноза есть практическая польза. Во-вторых,
**seasonal naive оказался сильным соперником** — суточный цикл в данных выражен
настолько ярко, что простое «как вчера в это же время» даёт MAE 8.46. Итоговый выигрыш
модели над ним составил 8.2 % по MAE и 8 процентных пунктов по MAPE.

Ошибка сильно зависит от сезона: на зимнем фолде MAE 12.10, на летнем — 4.02.
Отопительный сезон в Алматы даёт и более высокие концентрации, и большую их
изменчивость.

Обучающая выборка содержит 417 246 строк, а не втрое больше: все объекты университета
попадают в одну ячейку расчётной сетки источника и дают идентичные ряды, поэтому
дубликаты отсеиваются перед обучением. Проверено, что метрика от этого не меняется
(7.766 против 7.776 на выборке с дубликатами) — копии одного ряда информации не
добавляют, только время обучения.

> Приведённые цифры получены на LightGBM в контейнере. Если LightGBM в окружении
> недоступен (macOS без OpenMP), обучение переключается на
> `HistGradientBoostingRegressor`, и метрики немного хуже.

Модель не заменяет активную автоматически, если не превзошла baseline: `train()`
записывает артефакт в реестр, но указатель `active.json` остаётся на прежней версии.

## Тестирование

```bash
make test
```

```bash
make test-cov
```

152 теста, выполняются примерно за полторы секунды на SQLite — Docker для них не нужен.
Покрыты: расчёт AQI на граничных точках всех брейкпоинтов, конвейер очистки данных,
разбор ответов Open-Meteo (через `respx`), идемпотентность upsert, формирование
признаков и отсутствие утечки будущего, разбиение на фолды, все HTTP-эндпоинты,
авторизация админских маршрутов, таблица рекомендаций из технического задания и
мягкая деградация кэша при недоступном Redis.

Нагрузочное тестирование вынесено отдельно (Locust):

```bash
make loadtest
```

Профиль нагрузки и пороги описаны в [loadtest/README.md](loadtest/README.md).

CI (GitHub Actions) дополнительно прогоняет миграции на настоящем PostgreSQL в обе
стороны (`upgrade` → `downgrade` → `upgrade`), проверяет типы фронтенда и собирает
Docker-образы.

## Источники данных

| Источник | Роль | Статус |
|---|---|---|
| [Open-Meteo Air Quality API](https://open-meteo.com/en/docs/air-quality-api) | Основной: PM2.5, PM10, NO₂, O₃ + архив с 2022 года | Работает, ключ не нужен |
| [Open-Meteo Weather / Archive](https://open-meteo.com/) | Погодные признаки для модели | Работает |
| [Airkaz.org](https://airkaz.org) | Дополнительный: сеть наземных датчиков | Публичный эндпоинт отвечает 404 |

Адаптер Airkaz реализован, но выключен флагом `AIRKAZ_ENABLED=false`: при любой ошибке
он возвращает пустой список и пишет предупреждение в лог, а сбор данных продолжается
по Open-Meteo. Включается одной переменной окружения, если сеть снова откроет API.

### О расчёте AQI

Индекс считается кусочно-линейной интерполяцией внутри брейкпоинтов US EPA, с
усечением концентрации (PM2.5 — до 0.1 мкг/м³, PM10 — до целого), как требует методика.
Поддерживаются две редакции брейкпоинтов PM2.5: действующая `epa_2024` (по умолчанию)
и прежняя `epa_2012`, которая встречается в более старых источниках — выбор задаётся
переменной `AQI_BREAKPOINTS`.

Итоговый AQI — максимум частных индексов по PM2.5 и PM10. NO₂ и O₃ сохраняются в базе
как концентрации, но в индекс не входят: методика EPA требует для них других периодов
осреднения (1 и 8 часов) и единиц измерения (ppb), тогда как API отдаёт мгновенные
значения в мкг/м³.
