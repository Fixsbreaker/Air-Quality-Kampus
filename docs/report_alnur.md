### 2.2 Архитектура системы

Система построена по многослойной схеме с чётким разделением ответственности
(рисунок 1).

```
                    ┌──────────────────┐
                    │  Open-Meteo API  │  качество воздуха + погода
                    └────────┬─────────┘
                             │ httpx, раз в час (APScheduler)
                    ┌────────▼─────────┐
                    │  worker          │  сбор → очистка → расчёт AQI
                    │  (парсер + ML)   │  прогноз, ночное переобучение
                    └────────┬─────────┘
                             │
                    ┌────────▼─────────┐
                    │   PostgreSQL     │  measurements, weather, forecasts,
                    │                  │  users, alerts, model_runs
                    └────────┬─────────┘
                             │ SQLAlchemy
                    ┌────────▼─────────┐
                    │   FastAPI        │  /api/current, /history, /forecast,
                    │   + Swagger      │  /subscribe, /admin/report
                    └───┬──────────┬───┘
                        │          │
             ┌──────────▼──┐   ┌───▼────────────┐
             │ React SPA   │   │ Telegram-бот   │
             │ Recharts    │   │ aiogram 3      │
             │ Leaflet     │   │                │
             └─────────────┘   └────────────────┘
```

Рисунок 1 — Архитектура системы

Два архитектурных решения определяют облик системы.

**Вся доменная логика сосредоточена в программном интерфейсе.** Бот и веб-дашборд
являются тонкими слоями представления и не содержат правил расчёта. Благодаря этому
формула индекса и таблица рекомендаций существуют в единственном экземпляре, и
пользователь гарантированно видит одинаковый ответ в мессенджере и на сайте.

**Прогноз не вычисляется в момент запроса.** Фоновая задача раз в час записывает
результат работы модели в таблицу `forecasts`, а соответствующий эндпоинт лишь читает
её. Веб-процесс остаётся быстрым, а вычисления, занимающие секунды, не блокируют
обработку запросов.

## 3 ОПИСАНИЕ ПРОЕКТА

### 3.1 Предметная область и постановка проблемы

Алматы стабильно входит в число городов с наиболее загрязнённым воздухом. Основные
источники загрязнения — автотранспорт, частный сектор с печным отоплением и
теплоэлектроцентрали; усугубляет ситуацию географическое положение города в
предгорной котловине, где зимой возникают температурные инверсии, запирающие
загрязнённый воздух у поверхности.

При этом у университета не было инструмента, отвечающего на два практических вопроса,
которые ежедневно возникают у студентов и администрации:

1. можно ли сегодня проводить занятия физической культурой на улице;
2. можно ли открывать окна в аудиториях для проветривания.

Существующие ESG-инициативы университета оценивают то, что университет *выбрасывает*
(углеродный след, отходы, потребление энергии). Разрабатываемая система оценивает то,
чем студенты *дышат*, — и это принципиально иная задача.

## 4 МЕТОДОЛОГИЯ РАЗРАБОТКИ И ОРГАНИЗАЦИЯ КОМАНДНОЙ РАБОТЫ

### 4.1 Методология

В работе применялся подход, основанный на Scrum: работа разбивалась на недельные
итерации, в начале каждой формировался перечень задач, в конце проводилась
демонстрация результата наставнику. Ежедневно проводились короткие встречи,
на которых каждый участник отвечал на три вопроса: что сделано, что планируется,
что мешает.

Выбор итеративного подхода вместо каскадного был обусловлен характером задачи:
на старте не было известно ни качество данных источника, ни достижимая точность
прогноза. Каскадная модель потребовала бы зафиксировать эти параметры в техническом
задании заранее, что было бы недобросовестным допущением.

### 4.2 Организация работы с системой контроля версий

Применялась упрощённая модель Git Flow:

- `main` — защищённая ветка, всегда в работоспособном состоянии, изменения попадают
  только через Pull Request;
- `develop` — интеграционная ветка;
- `feature/*` — по одной ветке на задачу.

Сообщения коммитов оформлялись по стандарту Conventional Commits: тип изменения,
затрагиваемая область, краткое описание в повелительном наклонении. Такой формат
позволяет автоматически формировать список изменений и облегчает поиск по истории.

## 6 ИНДИВИДУАЛЬНОЕ ЗАДАНИЕ

### 6.1 Постановка задачи и требования

Задание: разработать слой сбора и подготовки данных и модель прогнозирования
концентрации PM2.5.

Требования к слою данных:

1. Автоматический сбор часовых значений по трём точкам кампуса.
2. Загрузка исторического архива глубиной не менее одного года.
3. Очистка ряда от дубликатов, выбросов и пропусков.
4. Расчёт индекса AQI по методике US EPA.
5. Отказ дополнительного источника не должен прерывать сбор.

Требования к модели:

1. Прогноз концентрации PM2.5 на 48 часов вперёд.
2. Обязательное сравнение с наивным прогнозом; модель, не превосходящая наивный
   прогноз, считается непригодной.
3. Валидация без утечки будущего.
4. Автоматическое переобучение по расписанию и сохранение версий модели.

### 6.2 Проверка источников данных

Техническое задание содержало прямое указание: до написания кода убедиться, что
источник отдаёт данные. Это указание было выполнено первым действием.

Таблица 6 — Результаты проверки источников

| Источник | Проверка | Результат | Решение |
|---|---|---|---|
| Open-Meteo Air Quality, текущие и прогноз | `GET /v1/air-quality?past_days=2&forecast_days=2` | 200 OK, полный часовой ряд | Основной источник |
| Open-Meteo Air Quality, архив | тот же эндпоинт с `start_date`/`end_date` | 200 OK, данные за прошлые годы доступны | Источник обучающей выборки |
| Open-Meteo Archive, погода | `GET /v1/archive` | 200 OK | Погодные признаки |
| Airkaz.org | `GET /map_data.php` | **404 Not Found** | Реализован как необязательный, выключен |

Отказ Airkaz был предусмотрен в техническом задании как один из рисков, поэтому
переработка архитектуры не потребовалась: Open-Meteo изначально планировался
основным источником.

При разборе ответов обнаружились три особенности, повлиявшие на реализацию.

Во-первых, ответ приходит «колонками»: массив меток времени и параллельные массивы
значений, выровненные по индексу. Разбор выполняется по позиции; если переменной в
ответе нет, колонка отсутствует целиком, и клиент подставляет пустые значения.

Во-вторых, пропуски приходят как `null`, а не как ноль. Различие принципиально: ноль
означал бы идеально чистый воздух, тогда как `null` означает отсутствие измерения.
Клиент это различие сохраняет.

В-третьих — и это оказалось самым важным — вместе с фактическими значениями источник
отдаёт собственный прогноз на двое суток вперёд. Последствия этой особенности описаны
в разделе 6.8.

### 6.3 Проектирование хранилища

Спроектированы три таблицы моей зоны ответственности.

Таблица 7 — Схема хранилища

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `measurements` | Часовые наблюдения по загрязнителям | `ts`, `source`, `location`, `pm25`, `pm10`, `no2`, `o3`, `aqi`, `aqi_category` |
| `weather` | Метеоусловия | `ts`, `location`, `temp`, `wind_speed`, `wind_dir`, `humidity`, `pressure` |
| `forecasts` | Прогноз модели | `created_at`, `target_ts`, `horizon_h`, `pm25_pred`, `aqi_pred`, `model_version` |
| `model_runs` | История обучений | `model_version`, `mae`, `rmse`, `baseline_mae`, `is_active` |

Принятые решения по проектированию:

**Все метки времени хранятся в UTC без указания часового пояса.** Перевод в
Asia/Almaty выполняется только на границе системы — при формировании ответа
программного интерфейса. Это решение снимает два класса проблем: расхождения в
поведении типов с часовым поясом между PostgreSQL и SQLite (последний используется
в тестах) и неоднозначность при переходе на летнее время.

**Уникальное ограничение на тройку `(ts, source, location)`** делает повторную
загрузку одного и того же периода безопасной: данные обновляются, а не дублируются.
Это важно, потому что источник уточняет свои значения задним числом, и один и тот же
час может выкачиваться несколько раз.

**Индекс по паре `(location, ts)`** покрывает основной сценарий запросов — выборку
ряда по одной точке за период.

**Индекс AQI хранится рассчитанным**, а не вычисляется при каждом запросе.
Расчёт выполняется один раз при записи наблюдения. Это денормализация, и она
сознательна: индекс запрашивается на порядки чаще, чем записывается.

### 6.4 Сбор и очистка данных

Конвейер сбора состоит из четырёх этапов: запрос к источнику, очистка ряда, расчёт
индекса, запись в базу.

**Клиент источника** реализован на httpx с повторными попытками при сетевых ошибках
и единообразной обработкой ошибок программного интерфейса.

**Конвейер очистки** выполняет четыре операции в строго определённом порядке
(листинг 1).

Листинг 1 — Конвейер очистки данных

```python
def clean_air_quality(records):
    """Полный конвейер очистки. Возвращает ряд и отчёт для логов."""
    report = CleaningReport(total_in=len(records))

    records, report.duplicates_removed = drop_duplicates(records)
    records, report.out_of_range = enforce_physical_limits(records)
    records, report.outliers_removed = remove_outliers(records)
    records, report.gaps_filled = interpolate_gaps(records)

    report.total_out = len(records)
    return records, report
```

Порядок операций не произволен:

1. **Дубликаты** удаляются первыми, иначе одна и та же метка времени попала бы в ряд
   дважды и исказила бы все последующие статистики.
2. **Выход за физические границы** (отрицательные значения, абсурдно высокие
   концентрации) отсекается вторым, чтобы не портить оценку медианы и разброса.
3. **Статистические выбросы** ищутся по скользящей медиане и медианному абсолютному
   отклонению (MAD). Робастные оценки выбраны потому, что среднее и стандартное
   отклонение сами смещаются под влиянием выброса, который требуется обнаружить.
4. **Короткие пропуски** заполняются линейной интерполяцией.

Отдельного пояснения требует решение **не заполнять длинные пропуски**. Заманчиво
восстановить любой провал и получить непрерывный ряд, но восстановленные «из воздуха»
сутки исказят обучение модели сильнее, чем честно оставленный пропуск: модель начнёт
учиться на прямой линии, которой в природе не было. Порог интерполяции установлен
в три часа.

При реализации обнаружился вырожденный случай: если в окне все значения одинаковы,
медианное абсолютное отклонение равно нулю, и деление на него невозможно. Для этого
случая введено отдельное правило: аномалией считается отклонение, сопоставимое с
самим уровнем сигнала.

**Запись в базу** реализована через upsert. Вместо конструкции `ON CONFLICT`,
специфичной для PostgreSQL, применён переносимый подход: выбрать существующие ключи,
разделить записи на вставляемые и обновляемые. Это позволяет одному и тому же коду
работать и на PostgreSQL в эксплуатации, и на SQLite в тестах, что радикально
ускорило прогон тестов — весь набор выполняется за 1,3 секунды и не требует Docker.

**Выкачка исторического архива** выполняется кусками по 90 дней, чтобы не превышать
ограничения источника на длину одного запроса. Результат: 26 352 наблюдения и столько
же записей погоды по трём точкам кампуса за год, время выполнения — 22 секунды.

### 6.5 Расчёт индекса качества воздуха

Индекс качества воздуха рассчитывается по методике Агентства по охране окружающей
среды США кусочно-линейной интерполяцией внутри интервалов концентраций:

```
I = (I_hi − I_lo) / (C_hi − C_lo) × (C − C_lo) + I_lo
```

где `C` — концентрация загрязнителя, `[C_lo; C_hi]` — интервал концентраций,
`[I_lo; I_hi]` — соответствующий интервал значений индекса.

Существенная деталь методики: перед расчётом концентрация **усекается, а не
округляется** — PM2.5 до одной десятой мкг/м³, PM10 до целого. Значение 12,99
превращается в 12,9, а не в 13,0. Пренебрежение этим правилом даёт расхождение с
официальными публикациями на границах категорий.

Реализованы две редакции таблицы интервалов для PM2.5: действующая редакция 2024 года,
в которой верхняя граница категории «Хорошо» снижена с 12,0 до 9,0 мкг/м³, и прежняя
редакция 2012 года, которая встречается в более старых источниках. Выбор задаётся
переменной окружения.

Итоговый индекс — максимум частных индексов по PM2.5 и PM10. Оксид азота и озон
сохраняются в базе как концентрации, но в индекс не включаются: методика требует для
них иных периодов осреднения (один и восемь часов) и иных единиц измерения (частей
на миллиард), тогда как источник отдаёт мгновенные значения в мкг/м³. Включение их
без пересчёта дало бы формально красивое, но неверное число.

### 6.6 Модель прогнозирования

#### 6.6.1 Постановка

Дан часовой ряд концентрации PM2.5 и сопутствующие метеоданные. Требуется в момент
`t` предсказать концентрацию в моменты `t + 1 … t + 48`.

Рассмотрены три схемы построения многогоризонтного прогноза.

**Рекурсивная**: предсказать `t + 1`, подставить предсказание как факт, предсказать
`t + 2` и так далее. Отвергнута: ошибка накапливается, и к сорок восьмому шагу модель
работает практически по собственным выдумкам.

**Отдельная модель на каждый горизонт**: 48 моделей. Отвергнута: каждая модель
обучается на меньшем объёме данных, а в реестре приходится хранить и согласованно
обновлять 48 артефактов.

**Прямая многогоризонтная** (выбрана): одна модель, номер горизонта подаётся как
признак. Даёт больше обучающих примеров на одну модель и один артефакт в реестре.

Дополнительно принято решение обучать **одну модель на все объекты наблюдения**,
подавая принадлежность к объекту как признак. Схема рассчитана на будущее подключение
наземных датчиков. Существенная оговорка: сейчас все здания университета расположены
в западной части Алматы, и расчётная модель источника не различает их — часовые ряды
за январь совпали полностью, включая случай, когда точки попадают в разные узлы сетки.
Поэтому перед обучением дублирующие ряды отсеиваются, и выборка содержит 417 246 строк
вместо 1 252 356.

Контрольное сравнение показало, что метрика от этого не меняется: MAE 7,766 после
дедупликации против 7,776 на выборке с дубликатами, при втрое меньшем времени
обучения. Отдельный эксперимент с точкой в другой части города (Медеуский район, где
концентрации примерно вдвое ниже) дал MAE 6,60 и выигрыш над наивным прогнозом 12,4 %.
Вывод: **объём обучающей выборки сам по себе ничего не даёт, значение имеет
разнообразие данных в ней.**

Циклическое кодирование заслуживает пояснения. Если подать час суток целым числом от
0 до 23, модель увидит максимальный разрыв между значениями 23 и 0, хотя это соседние
часы. Пара синус-косинус переводит час в точку на окружности, и соседние часы
оказываются рядом в пространстве признаков. То же соображение применено к направлению
ветра, где 359° и 1° — практически одно и то же направление.

#### 6.6.3 Валидация

Стандартная перекрёстная проверка со случайным перемешиванием для временных рядов
неприменима: она позволяет обучаться на будущем и проверяться на прошлом, из-за чего
метрика получается неоправданно оптимистичной.

Применено расширяющееся окно по времени: обучение — всё прошлое до границы, проверка —
следующий блок, между ними **зазор длиной в максимальный горизонт прогноза**.

Механизм утечки, который закрывает зазор, следующий. Строка признаков, относящаяся к
моменту `t` и горизонту 48, имеет целевое значение в момент `t + 48`. Если тестовый
период начинается сразу за обучающим, целевые значения последних обучающих строк
попадают внутрь тестового периода: модель фактически видела ответы, которые её затем
просят предсказать. Зазор в 48 часов это исключает.

Отсутствие утечки в самих признаках проверяется отдельным тестом: последние сутки
ряда заменяются заведомо неверными значениями, после чего признаки в середине ряда
обязаны остаться неизменными.

Полученные результаты требуют честной интерпретации, и три наблюдения здесь важнее
самих цифр.

**На горизонте один час наивный прогноз лучше модели** — проигрыш составляет 36 %.
Это не дефект реализации, а свойство задачи: за час концентрация меняется мало,
инерция объясняет почти всю динамику, а модель добавляет к ней собственный шум.
Начиная с трёх часов модель уверенно выигрывает. Практической ценности этот проигрыш
не имеет: решение о переносе занятия принимается не за час до него.

**Сезонный наивный прогноз оказался сильным соперником.** Суточный цикл в данных
выражен настолько ярко, что простое «как вчера в это же время» даёт MAE 8,46 против
7,77 у модели — выигрыш составил 8,2 %. По относительной ошибке разрыв заметно
больше: 34,3 % против 42,3 %, то есть модель точнее работает на низких концентрациях.

**Ошибка сильно зависит от сезона.** На зимнем фолде MAE составляет 12,10, на летнем —
4,02, то есть отличается в три раза. Отопительный сезон даёт и более высокие
концентрации, и большую их изменчивость. При случайном перемешивании выборки этот
эффект остался бы полностью незамеченным, и заявленная точность модели была бы
средней по больнице.

#### 6.6.5 Реестр моделей и защита от деградации

Артефакт модели сохраняется в формате joblib, рядом — файл с метриками и метаданными
обучения. Отдельный файл-указатель содержит имя активной версии; прогноз использует
именно её. Откат к предыдущей модели сводится к правке одной строки, без пересборки
образа.

Заложено правило: **модель не становится активной автоматически, если не превзошла
наивный прогноз**. В этом случае артефакт и запись в истории обучений сохраняются,
в журнал пишется предупреждение, но указатель активной версии не изменяется. Это
защищает эксплуатируемую систему от деградации после неудачного переобучения —
например, если за прошедшие сутки в базу попал испорченный участок данных.

### 6.7 Кэширование прогноза

Расчёт прогноза выполняется фоновой задачей раз в час, а запрашивается он на каждое
открытие дашборда и на каждую команду бота. Ответ эндпоинта прогноза кэшируется в
Redis — нереляционном хранилище типа «ключ — значение», подключённом напарником.

Моя часть — кэширование прогноза и, что важнее, **инвалидация по событию**. Времени
жизни записи здесь недостаточно: момент устаревания данных известен точно — это
завершение сбора новых наблюдений или пересчёт прогноза. Поэтому обе фоновые задачи
принудительно сбрасывают соответствующие ключи по префиксу, а срок жизни остаётся
лишь страховкой на случай, если сброс не отработал.

Ключи строятся с учётом параметров запроса: глубина прогноза задаётся клиентом, и
ответы на 24 и 48 часов различны. Без параметра в ключе пользователь, запросивший
сутки, получил бы закэшированный ответ на двое суток.

### 6.9 Трудности и способы их преодоления

**Трудность 1. Дополнительный источник данных оказался недоступен.**

Публичный эндпоинт сети датчиков Airkaz отвечает кодом 404. Этот риск был предусмотрен
техническим заданием, поэтому переработка архитектуры не потребовалась. Адаптер
написан и покрыт тестами, но при любой ошибке возвращает пустой результат и пишет
предупреждение в журнал; сбор по основному источнику продолжается независимо.
Источник включается одной переменной окружения, если сеть снова откроет доступ.

Вывод, который я вынес: внешняя зависимость должна быть спроектирована так, чтобы её
отказ был штатным сценарием, а не аварией.

**Трудность 2. Прогноз источника принимался за наблюдение.**

Самый существенный дефект, обнаруженный при сквозной проверке уже готовой системы.
Программный интерфейс Open-Meteo вместе с фактическими значениями отдаёт собственный
прогноз на двое суток вперёд. Эти строки записывались в таблицу наблюдений наравне
с фактами. Как следствие, модуль прогнозирования брал в качестве «последнего
известного часа» строку, относящуюся к ещё не наступившему моменту, и весь горизонт
прогноза уезжал на двое суток вперёд. Внешне система выглядела работающей: прогноз
отдавался, графики строились, ошибок в журнале не было.

Дефект проявился только при ручной сверке: в ответе оказалось 19 точек вместо 48,
и первая из них относилась к послезавтрашнему дню.

Исправление: функция загрузки ряда получила верхнюю границу по времени, равную
текущему моменту. Строки с будущими метками по-прежнему сохраняются в базу — позже
они перезаписываются фактическими значениями и становятся полезной историей, — но
в обучение и в построение признаков не попадают. Добавлен тест-регрессия, который
проверяет отсечение.

Вывод: проходящие тесты и отсутствие ошибок в журнале не означают, что система
работает правильно. Сквозная проверка на реальных данных обнаружила то, чего не
увидели ни модульные тесты, ни ревью.

**Трудность 3. Модель едва превзошла сезонный наивный прогноз.**

Первые запуски давали выигрыш над сезонным наивным прогнозом в пределах двух-трёх
процентов, что вызывало сомнение в целесообразности модели. Разбор показал, что дело
не в ошибке реализации: суточная сезонность в данных настолько выражена, что наивное
«как вчера» действительно является сильным прогнозом.

Ситуация была рассмотрена в двух плоскостях. Во-первых, добавление погодных признаков
и признака отопительного сезона дало заметное улучшение относительной ошибки.
Во-вторых, был отдельно проанализирован выигрыш по горизонтам, и выяснилось, что
усреднённая метрика скрывает существенно разное поведение: на коротких горизонтах
модель проигрывает, на средних и длинных выигрывает от 8 до 29 процентов.

Техническое задание прямо предписывало на этот случай: «если не помогло — честно
указать в отчёте: это тоже валидный результат». Результат приведён без приукрашивания,
включая проигрыш на горизонте один час.

**Трудность 4. Вырожденный случай в детекторе выбросов.**

При тестировании обнаружилось, что на искусственно ровном ряде детектор выбросов не
срабатывает: медианное абсолютное отклонение обращается в ноль, и деление на него
невозможно. В реальных данных такая ситуация практически не встречается, но
некорректное поведение на границе — это дефект. Введено отдельное правило для этого
случая.

**Трудность 5. Различия окружений.**

Библиотека LightGBM на macOS требует библиотеку OpenMP, которая по умолчанию не
установлена: пакет успешно импортируется, но падает при загрузке нативной библиотеки,
причём с ошибкой типа `OSError`, а не `ImportError`. Обработчик, перехватывавший
только `ImportError`, эту ситуацию пропускал.

Решение: перехватывать оба типа ошибок и переключаться на реализацию градиентного
бустинга из scikit-learn — алгоритмически это тот же гистограммный бустинг, но без
внешних зависимостей.

Побочный результат оказался содержательным. Метрики, приведённые в разделе 6.6.4,
получены на LightGBM в контейнере, где OpenMP присутствует. Прогон тех же данных на
запасной реализации дал MAE 8,27 против 7,78 и выигрыш над сезонным наивным прогнозом
2,3 % вместо 8,1 %. Разница показывает, что вклад в результат вносит не только
постановка задачи и набор признаков, но и конкретная реализация алгоритма, — при этом
качественные выводы (проигрыш на коротком горизонте, сезонная зависимость ошибки)
сохраняются на обеих реализациях.

Вывод: код должен корректно работать в окружении, отличном от того, в котором его
писали, и различие окружений само по себе может быть источником данных для анализа.

## ПРЕДЛОЖЕНИЯ

**По развитию проекта:**

1. **Отдельная обработка коротких горизонтов.** На горизонтах один-два часа наивный
   прогноз точнее модели. Логично отдавать на этих горизонтах именно его, а модель
   включать начиная с трёх часов. Это улучшит итоговую метрику без усложнения модели.

2. **Использование прогноза погоды как признака.** Сейчас модель использует погоду
   в момент построения прогноза. Источник отдаёт и прогноз погоды на те же 48 часов —
   это признак, относящийся к целевому моменту, и он должен заметно помочь на дальних
   горизонтах.

3. **Интервальный прогноз вместо точечного.** Квантильная регрессия позволит выдавать
   не одно число, а диапазон, что честнее отражает неопределённость и полезнее для
   принятия решений администрацией.

4. **Установка собственных датчиков на кампусе.** Модельные данные источника
   интерполируются по сетке и не отражают локальных особенностей — близости
   магистрали, внутреннего двора, высоты этажа. Два-три недорогих датчика позволили
   бы откалибровать модельные значения по фактическим замерам.

**По организации практики:**

5. **Предусмотреть в программе практики отдельный день на сквозное тестирование.**
   Наиболее серьёзный дефект был обнаружен именно на этом этапе, и обнаружен почти
   случайно, поскольку отдельного времени на такую проверку календарным планом не
   предусматривалось.

6. **Ввести обязательное взаимное ревью кода между практикантами** там, где практику
   проходят несколько студентов. В нашем случае замечание напарника по одной части
   системы напрямую помогло найти аналогичную ошибку в другой.

7. **Рекомендовать фиксировать проверку исходных данных до начала разработки**
   отдельным документом. Требование технического задания «пока не убедился, что
   источник отдаёт данные, не пиши ни строчки кода» оказалось самым полезным
   указанием во всём документе.
